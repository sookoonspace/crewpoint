# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CrewPoint — Flutter (Dart SDK `^3.11.5`) collaborative event-management app: events with RBAC, tasks, Splitwise-style budget/settlements, real-time chat, push notifications. Backend is Firebase (Auth, Firestore, Storage, Cloud Functions v2 in TypeScript, Messaging). Three flavors map to three Firebase projects: `crewpoint-dev` / `crewpoint-stg` / `crewpoint-prod`.

flutter test test/journeys/                                 # robot journey tests only
flutter test --tags screenshots --update-goldens            # regen screenshots/ (skipped by default via dart_test.yaml)
flutter test test_acceptance/                               # acceptance suite; red can be a planned gap

# Lint

## Architecture

Keep the Architecture sections below, including RBAC and the Firestore data model, up to date as each Stage 1 slice lands.

### Layering

`lib/app/core/` (cross-feature) + `lib/app/features/<feature>/` where every feature is split `data/` (repositories, remote services, pure utilities) · `domain/` (models, repository interfaces) · `application/` (Riverpod notifiers/providers) · `presentation/` (screens, widgets). Features: `auth`, `budget`, `chat`, `dashboard`, `onboarding`, `participants`, `profile`, `registration`, `tasks`, `dev`.

### Firestore is the source of truth; Drift is a read mirror

`EventRepository`, `TaskRepository`, `ExpenseRepository`, `ChatRepository` all follow the same shape:

- Writes go straight to Firestore (the SDK's offline queue handles reconnect).
- A per-key (`uid`, `eventId`, `eventId/taskId`) Firestore listener mirrors snapshots into Drift; the UI watches the Drift stream so cold starts render instantly. Mirrors write each snapshot in one Drift transaction: the first reconciles everything, later ones apply only `docChanges` (Req 59), so one changed document updates the screen once.
- **`kIsWeb` forks to the raw Firestore stream** — Drift on web is Wasm/in-memory, so mirroring buys nothing there. Any new mirrored stream needs the same fork.
- Mirror subscriptions are torn down through `ref.onDispose(() => repo.disposeMirror(key))` in the provider, not by the repository itself.

Drift schema is at v18 with explicit migrations in `lib/app/core/database/app_database.dart`; tables are declared inline there, DAOs in `database/daos/`. Bumping the schema means adding a migration step *and* a `test/database/migration_vN_to_vN+1_test.dart`.

### Providers

`lib/app/core/providers.dart` is the composition root — nearly every service, repository, and stream provider is declared there by hand. **Riverpod codegen is not used** despite `riverpod_generator` being in dev_dependencies: notifiers are hand-written `Notifier`/`NotifierProvider`. Follow the existing style rather than introducing `@riverpod`.

### Router

`createRouter(...)` in `lib/app/core/router/app_router.dart` is constructed **once** in `_MyAppState.initState` and driven by a `_RouterRefresh` `ChangeNotifier` passed as `refreshListenable`. Auth/onboarding changes call `refresh()` — never rebuild or recreate the router (the old pattern tore down the route stack). `onRouteChanged` defers its `currentRouteProvider` write onto a microtask because GoRouter's redirect runs during build and Riverpod 3 forbids mid-build mutation. `currentRouteProvider` exists so FCM foreground banners can suppress themselves when the user is already on the target screen.

### Test seams

Every platform call is behind an interface so tests never touch a real SDK: `IAuthService` (also email sign-in links and phone codes, #241), `IIncomingLinkSource` (App Links and Universal Links, including the launch link; `FakeIncomingLinkSource`), `IUserRepository`, `IFcmGateway`, `IChatService`, `IUrlLauncher`, `IFileExporter`, `IFilePicker`, `IImportUploader`, `IQrRenderer`, `IAppBadgePlatform`, `INotificationChannels`, `IDeviceTimezone`, `IAppInfo`, `IAppConfigSource`, `IPageReloader`, App Check (`AppCheckStarter`, started only in `main`, reCAPTCHA Enterprise on the web with `APP_CHECK_WEB_KEY` from `.env.<flavor>`, off without it; `docs/ops/app-check-and-public-pages.md`), `ICrashReporter` (Sentry, started only in `main`; `crashReporterProvider` sends nothing otherwise, and every report goes through `scrubEvent`, so no user identity leaves the device; on web `main` runs in `runWithCrashReporting`'s zone and Sentry's JavaScript SDK drops what it catches itself, because that path skips the scrubbing), `MemberCalls` (role and member callables; `FakeMemberCalls` in `test/harness/` writes what the server would), `IConnectivity` (`FirestoreConnectivity` asks the server for `config/app`, for saves that must not queue offline), `ICoverCache` (cover photos on the device), `ILanguageAccountStore` (the account's language), `IFontLoader` (runtime fonts), `AppLifecycleSource`, and injected `Clock` for time-sensitive logic (e.g. the settle-confirm window). Adding a new platform dependency means adding a seam + provider, not calling the plugin from a widget.

Conditional imports handle compile-time platform splits: `database/connection/native.dart` vs `web.dart`, `services/file_export_service_native.dart` vs `_web.dart` (`if (dart.library.html)`).

### RBAC

Double-enforced through the permission catalogue (#66). The client gates UI with `event.can(uid, permission)`, `event.contributes(uid)` (adding your own expense or task, which Observer and Vendor cannot; they also read only tasks assigned to them and expenses they paid or share in, unless their role holds `tasks.manage`, `money.read` or `expenses.readAll`, so their queries filter on `assigneeId` and `involvedUids`, chosen by `taskReadScopeProvider` and `expenseReadScopeProvider`; without `chat.send` the chat entries are hidden) and `event.isOwner(uid)`. For the signed-in person these read `myPermissions` from their member document, so they update live when a role changes. `firestore.rules` checks one permission with one member-document read (reading chat needs `chat.send`), and functions use `requirePermission` in `functions/src/events/members.ts`. Check the named permission, never `creatorId`, `adminIds` or a role name. Privileged mutations are callables, not direct writes — `createEvent`, `changeEventCurrency`, `setMemberRoles`, `saveEventRole`, `deleteEventRole`, `saveCrew`, `setCrewMembers`, `deleteCrew`, `offerOwnership`, `acceptOwnership`, `cancelOwnershipOffer`, `joinEvent`, `removeEventMember`, `promoteToAdmin`, `demoteAdmin`, `deleteEvent`, `markTaskComplete`, `saveExpense`, `recordSettlement`, `disputeSettlement`, `createInviteLink`, `updateInviteLink`, `generateInviteCode`, `saveRegistrationSettings`, `claimEventSlug`, `deleteUserAccount`. Firestore triggers push only to people who may read the record, through `functions/src/events/access.ts`, which mirrors the rules (`onUrgentMessageCreated`, `onTaskAssigned`, `onExpenseCreated`, `onSettlementDisputed`, `onMemberJoined`, `onTaskDueScheduled`, `onDigestSummary`) drive push. `onEventStatusScheduled` moves events to `live` and `ended`. All exported from `functions/src/index.ts`; `docs/cloud-functions-guide.md` holds the authoritative Function Registry.

Firestore data model: `events/{eventId}` with `messages`, `tasks` (+ `tasks/{id}/checklist`), `taskBudgets`, `expenses`, `members`, `profiles`, `roles`, `crews`, `groups`, `participants` (+ `participants/{id}/private/details`), `linkRequests`, `participantKeys` and `ownership` (the pending offer) subcollections; `serverSecrets/{name}` and `serverConfig/{name}` (no client access); `mailOutbox/{id}` (server only); `organizers/{uid}` (a person's personal organizer, written only by the server, holding `verified`); `event_invites/{code}`; `eventSlugs/{slug}` (an event's link name, server only); `rateLimits/{key}` (public-call counts, server only); `config/app` (public read, no client write; `minVersion` and optional `storeUrls.ios` / `storeUrls.android`, set from the console); `users/{uid}` with `private`, `chatReads`, `eventMutes` subcollections, readable only by its owner.

Who reads every expense is the event's `settings.expenseAccess` (#72): `everyone` (contributors, plus Observers and Vendors only with `includeNonContributors`), `involved`, or `selected` (`roleIds` and `uids`); missing means `everyone`. Only `setExpenseAccess` changes it, logging to `settingsLog`, and `functions/src/events/expenseAccess.ts` turns it into `expenses.readAll` on member documents, so `memberDoc` and `rebuildMember` take the event's access and every caller passes `expenseAccessOf(eventData)`. Rules let anyone read expenses they paid or share in, and every expense only with `money.read` or `expenses.readAll`. `getMyBalance` gives a limited member their balance from all expenses. In the app, `event.expenseAccess` mirrors the setting (`ExpenseAccess` in `dashboard/domain/models/expense_access.dart`), `readsAllExpenses` checks only `money.read` and `expenses.readAll`, and the "Who can see expenses" screen (`settings/expenses`, `ExpenseAccessScreen`) saves through `MemberCalls.setExpenseAccess`. When someone cannot read every expense, the event budget page, its PDF export (`runExpenseExport(ledger:)`), the global Budget tab and the leave warning use `myBalanceProvider` / `myBalanceCallProvider` instead of working balances out from the expenses they see. Chat settlement notices carry an amount only when everyone who can read chat reads every expense (`chatShowsAmounts` in `access.ts`). The event Budget (Spec #186, #202) is `budget` (`EventBudgetPage`: spent, your balance with Settle up from `myBalanceSummary`, balances, settle-up and the expenses with settlements as Paid) and `budget/:expenseId` (`ExpenseDetailPage`, read view with Edit in place and Delete), whose page comes from `expensePage` in the router, shared with the test harness: from 840 px the list with that expense beside it through `CpListDetail`. `ExpenseModal` is now a full-page form, opened with `show` or in place with `onCancel`.

Money and names are kept apart from what everyone reads (#71), because rules cannot hide one field. A task's budget figure is `taskBudgets/{taskId}` (`estimate`), which needs `budget.read` to read and `budget.edit` to set or clear, and tasks never carry `budgetEstimate`. Other people's names, photos and payment handles come from `events/{eventId}/profiles/{uid}`, which only the server writes (`onMemberProfileSync`, `onUserProfileSync`): anyone in the event reads it, and someone who leaves keeps only their name there. Profiles also carry `sortName` (lower-case name) and `inEvent` (false after leaving), indexed together for the member picker (#80). `deleteUserAccount` removes every profile of the person. In the app, names load only for the people a screen shows (Req 43a): `peopleByIdProvider(PeopleKey(eventId, uids))` reads exactly those uids, one `eventProfileProvider` each (falling back to your own `users/{uid}` until the server copies it), lazy lists read each row's name in the row, and `fetchPeople` reads a few once. Pay links read handles through `IUserRepository.watchEventProfile`; never read someone else's `users/{uid}`, and never load every profile in an event. Choosing people goes through `MemberPickerSheet` (`pickOne`, `pickMany`; `IUserRepository.fetchMemberPage`, 30 a page by `sortName` prefix): the task assignee (`AssigneePicker`), who shares an expense, transfer ownership, and `ChosenPeopleList` for crews, group adults and expense access. Event tiles and counts use `event.memberCount` (the server's count, mirrored in Drift, falling back to the array). `budget/domain/models/large_event.dart` holds the 50-member line: past it a new equal split must name who shares it (with an explicit "Split with everyone"), and the budget page shows you and the 20 largest balances and transfers, reading only those names; exports read the rest when run. `taskBudgetsProvider(eventId)` streams figures straight from Firestore for `budget.read` holders and is empty for everyone else. The task screens merge it with `withBudgets`, and the Drift `tasks.budget_estimate` column stays empty. The budget field needs `budget.edit` and the "Has budget" filter `budget.read`; `updateTask(..., budgetEditedBy:)` saves a changed figure in the same batch.

System templates (#89, Req 62): six versioned JSON files in `assets/templates/` (Blank, Party, Wedding, Cricket tournament, Golf outing, Convention; `index.json` gives the order), each setting modules, labels, renamed roles (`{name, base}`), fields, categories, the attendance policy and expense access. They are the only place event-specific words may appear. `npm run gen:templates` copies them to `functions/templates/` for the server, and a test fails if the copy falls behind; edit only `assets/templates/`. `createEvent` takes a checked `templateId` and copies the template into the event, its fields and roles in one transaction, with `templateVersion`, so later template versions never change an event. In the app, `/dashboard/create` is the picker (`TemplatePickerScreen`, `templateCatalogueProvider`), and `/dashboard/create/:templateId` the form; Party and Blank (`fastPath`) need only a title and a date. Saved templates (#90, Req 65): `saveAsTemplate` (`event.manage`, `MemberCalls.saveAsTemplate`) keeps an event's configuration in `users/{uid}/templates/{id}` (owner reads and deletes; only the server writes): modules, labels, attendance policy, categories, expense access by role (named people dropped), fields and changed roles with their `permissions`, plus `baseTemplateId`. Never people, money, messages, dates, venues or the title. `createEvent` takes `savedTemplateId` for its owner only; the picker lists them first (`myTemplatesProvider`, `/dashboard/create/mine/:savedTemplateId`). Account deletion removes them. Follow-up setup (Req 64): after creating from a template without `fastPath`, the app opens `setup` (`SetupChecklistScreen`), a skippable list of dates, places, schedule, questions and people, each ticked when done; Event settings links back to it. Tests feed templates with `systemTemplatesOverride()` from `test/harness/system_templates.dart`, and `fakeCreateEventCall` applies them as the server does.

Events carry `templateId`, `organizerId`, `timeZone`, `venues`, `currency`, `languages`, `status`, `modules`, `labels`, `settings`, `capacity` and `memberLimit`, and need only a title. An optional cover photo (Spec #186, #198) is `cover: {path, updatedAt}` on the event, always `events/{eventId}/cover.jpg` in Storage (`storage.rules`: read with a member document, write and delete with `event.manage`, JPEG, PNG or WebP under 5 MB; `firestore.rules` checks the field names only that file); a missing field means none. It is mirrored in Drift (`cover_path`, `cover_updated_at`). `EventCoverService` (`eventCoverServiceProvider`) picks it at 1,600 px, quality 85, through `IImageService`, uploads it and sets the field, or clears the field and deletes the file; `deleteEventCompletely` deletes it with the event. `coverBytesProvider(cover)` reads the device copy for that version (`ICoverCache`, files natively, memory on web) or downloads and keeps it, so a replaced photo is never stale and thumbnails show offline. `EventCoverBanner` and `EventCoverThumb` show it, or without one the accent banner with `eventIcon(event, templateIcons)`: the template's icon, else `iconForEventType`, else a plain event icon. Storage CORS per flavor is in `docs/ops/storage-cors.md`. `eventType` survives on older events as display text only. Older events lack the new fields, so reads must fall back to the same defaults as `createEvent`.

The schedule (#81) is `sessions/{sessionId}`: `title`, `startAt`, optional `endAt`, `timeTbc` (a placeholder time), `venueId` or `locationTba`, free-text `type` (suggested from types already used), `tags`, `capacity`, `eligibility` (`categoryIds` and `filterTags`, empty for everyone, one of each when both are named; `SessionEligibility.admits`) and `hidden`, a draft only `schedule.edit` reads, so anyone else lists with `hidden == false`. Clients write it directly with `schedule.edit`; rules apply the `schedule` module and the same status rules as tasks (`event.canEditSchedule`). `SessionRepository` mirrors it into the Drift `sessions` table (replacing an event's rows in one transaction, with the `kIsWeb` fork), read through `sessionListProvider(eventId)`. Venues on the event hold `address` (empty means to be announced), `mapUrl` (http or https only) and `directions`; `mapLinkFor` opens the organizer's link or a search for the address. `schedule/domain/models/schedule.dart` groups by day in the event's zone (`byDay`) and by venue (`byVenue`, every venue, then sessions without one). Screens (Spec #186, #203): `schedule` (`ScheduleScreen`, by day with a button per day that jumps to it, or by venue with `VenueCard`; rows are `SessionTile`, the start time beside the title with Now, who it is for, capacity, a placeholder time and Hidden draft as tags) and `schedule/:sessionId` (`SessionScreen`: details for readers, a form in the Person form's pattern for editors, `new` to add).

Attendance (#82, Req 50): the event's `settings.attendancePolicy` (`arrivalToDeparture`, `invitedOnly`, `everyone`, `bySession`; missing means everyone), a session's own `attendance` overriding it, and only exceptions stored: participants' optional `arrivalAt`/`departureAt` and session-ID lists `optOuts`, `signUps`, `invitedTo`, and groups' `invitedTo`. Only `participants.edit` changes invitations (rules); a group's linked adults set their own people's stay, opt-outs and sign-ups. `attends()` exists twice, `schedule/domain/models/attendance.dart` and `functions/src/schedule/attendance.ts`, and both run the cases in `functions/test/fixtures/attendance_cases.json`, so change them together. `setAttending` turns a switch into the smallest exception. The participant screen shows `AttendanceSection`, and `GroupSheet` sets group invitations. The `agenda` route (`AgendaScreen`, hub entry Agenda) builds the viewer's agenda with `buildAgenda` and `nowAndNext` (a session with no end lasts an hour; time from `clockProvider`/`minuteProvider`) from their own records: `MyRecordsRepository` mirrors their participant record (`uid ==`), their groups' people (`groupId in`) and groups into the Drift `my_records` table (`myRecordsProvider`). Someone with no record sees the whole schedule. Offline (Req 74): the sessions, tasks, chat and agenda mirrors record `mirror_syncs` (last server snapshot, and whether reading from cache, through `includeMetadataChanges`), and `LastUpdatedNote(mirrorKey)` shows "Offline. Last updated …" on those screens.

Counts (#83, Req 52): `functions/src/counts/stats.ts` (`computeStats`, pure) counts active people by category and by every single-choice, multi-choice and yes/no field, private ones included (totals only), and each session through the shared `attends()`; unanswered and uncategorised count under `_none`. Changes to participants, groups, sessions, fields, private answers or the policy and categories queue the event in `countsQueue/{eventId}` (`onCountsInputWritten`, `onCountsPrivateWritten`, `onCountsSettingsChanged`); `onCountsScheduled` counts each queued event once every 5 minutes into `events/{id}/stats/current` with `updatedAt`, and `recalculateCounts` (`counts.read`, `MemberCalls.recalculateCounts`) counts now. Rules let only `counts.read` read `stats`, and nobody write it or the queue. In the app, `counts` (`CountsScreen`, hub entry for `counts.read`) reads `eventStatsProvider` (gate it on `counts.read` at the caller), shows when counts were last updated and offers "Recalculate now"; the settings capacity line uses the counts total when there is one.

Export and freeze (#84, Req 53, 54), both needing `reports.export`: the counts screen exports counts as CSV in the app (`countsCsv` in `counts/domain/count_export.dart`, one row per session, private fields only when chosen), the roster through the `exportRoster` callable (private answers and birth dates only with `includePrivate` and `participants.readPrivate`), and changes since a freeze (`countChanges`, `changesCsv`). `freezeCounts` counts now and keeps the numbers in `countFreezes/{id}` (read with `counts.read`, written only by the server) with the date, who froze them and a note; the screen compares the live counts with the latest freeze or an earlier one. Every CSV cell goes through `neutraliseCsvCell` (Dart) or `toCsv` (TypeScript).

Chat paging (#85, Req 57, 58): `IChatService.latestMessages` listens to the latest `chatPageSize` (50) messages and emits `ChatChanges` from `docChanges`: upserts, deletions (`deletedFromWindow` tells a deletion from a message that only fell out of the window), and the whole window on the first snapshot and the first from the server, which clears messages deleted while away (`staleInCache`). `ChatRepository` applies each change set in one Drift transaction (`ChatMessagesDao.applyChanges`), keeps `kind` (settlement bubbles on mobile), trims the device copy to `maxCachedRows` when the mirror starts, and keeps the `kIsWeb` fork folding the same changes in memory. Older pages come from `olderMessages` / `fetchOlder` into `olderMessagesProvider` (in memory, not mirrored); `EventChatPage` shows "Show earlier messages" above the oldest message, or, offline, that earlier messages need a connection. In the new look (Spec #186, #205) the inbox is one card of `ConversationTile` rows with the event's cover, and `MessageBubble` shows urgent messages in red and settlements in green, each with its icon and label; `CriticalAlertModal` and `DisputeSheet` open through `showCpSheet`.

Chat summary (#86, Req 57a): `onChatMessageWritten` keeps `events/{id}/chatSummary/current` (`count`, `latest`, `lastUrgentAt`/`lastUrgentSenderId`; read with `chat.send`, written only by the server) and moves the sender's `users/{uid}/chatReads/{eventId}` (`lastReadAt`, `readCount`) past their own message; `migrateToMembers.ts` builds missing summaries. The app's `globalInboxProvider` reads `chatSummaryProvider` and `eventChatReadStateProvider` (`ChatReadState`, mirrored in Drift `chat_reads` with `read_count`) and works out unread counts and urgent status with `inboxUnread`, loading no messages. `EventChatPage` marks the chat read with the summary's count when opened and as messages arrive. The preview text is the message's own, so it shows an amount only when the message does.

Event dates are calendar dates: with `dateOnly: true` they are stored as midnight UTC on the chosen date, and read through `event.displayStart` and `displayEnd`, never `startDate` directly. Other times show through `event.inZone`, and a chosen day converts with `event.startOfDay`. Helpers are in `core/format/event_time.dart`.

`events/{id}/members/{uid}` holds `uid`, `roleIds`, `crewIds`, `permissions`, `participantId` and `joinedAt`, plus `groupIds` for someone linked to a group.

Participants (#75) are people attending, with or without an account, children included: `name`, `sortName` (lower-case, for paged prefix search), `groupId`, `isChild` and `status`, with `uid` (a linked account) and `externalId` (an import's ID) written only by the server. A birth date lives in `participants/{id}/private/details` as `YYYY-MM-DD`. Groups (`name`, `sortName`, `adultUids`) are written only by `saveGroup`, `setGroupAdults` and `deleteGroup`, which keep `groupIds` and `group.editOwn` on member documents in step. Rules: the roster needs `participants.read`; anyone is added or edited with `participants.edit`, or by a linked adult for their own group (`inMyGroup` reads `groupIds`); private details need `participants.readPrivate` or a linked adult of the group. A linked adult lists with `groupId in` their group IDs. Rosters are never mirrored. Custom fields (#76) are defined in `fields/{fieldId}` by `event.manage` (`type` text, number, date, singleChoice, multiChoice or yesNo; `scope` participant or group; `visibility` standard or private). Standard answers sit in `fields` on the participant or group, which a group's adults may update without the group callables; private answers sit in that record's `private/details`. The app writes `filterTags` (`fieldId=value`, standard choice and yes/no answers only) and `categoryId`, worked out from the private birth date by age rules in `settings.categories`, so the roster can filter without reading private data and reports show age bands. One composite index per combination of `groupId`, `categoryId` and `filterTags` with `sortName`. Roster import (#77): the app uploads a CSV to Storage at `events/{id}/imports/{jobId}.csv` and creates `imports/{jobId}` (`targets` maps each column, `mode` `dryRun` or `apply`, `status` `queued`); `onImportQueued` runs it with the pure `functions/src/imports/plan.ts` and writes `report` and `progress`. A client may only create a queued job, or queue a `checked` one again. Imported people carry a server-only `imported: true`, and an imported email sits in their private details. `cancelImportedGroups` confirms missing groups; `cleanupImports` removes files after 7 days. `npm test` starts the Storage emulator too. In the app, `people/import` (`ImportScreen`, before `people/:participantId` in the router) picks a file through `IFilePicker` (`file_selector`), previews and guesses the mapping with `import_mapping.dart` (matching the event's own words, so no banned word is hard-coded), uploads through `IImportUploader` and watches the job (`importJobProvider`, `recentImportsProvider`). Tests use `test/harness/fake_import.dart`, whose `FakeImportServer` answers queued jobs. Account linking (#78): `linkMyParticipants` links a signed-in person whose **verified** email (`email_verified` on the token) or verified phone (the token's `phone_number`, set once the SMS code is entered; Spec #233 Req 13, #237) matches the email or phone in a participant's private details, using `decideLinks` in the pure `functions/src/participants/linking.ts` (an email match and a phone match on two adults are two adults; cases in `functions/test/fixtures/linking_cases.json`): exactly one adult record links, never a child or a name; two or more adults, or only children, open `linkRequests/{uid}` (read with `participants.readPrivate`), which `resolveLinkRequest` settles. Linking makes someone new a Participant (an existing member keeps their roles), sets `participantId`, and adds them to the record's group (`adultUids`, `groupIds`); drafts wait for anyone not yet in the event, and ended or full events are skipped. A linked person reads their own record and its private details (`uid ==`). Deleting an account (`participants/accountData.ts`) turns linked records into unnamed entries (`name` empty, server-only `anonymised: true`, keeping age band, status, group and `filterTags`); while the event has not ended, `participantKeys/{participantId}` keeps HMAC keys of the email, phone and import ID (secret in `serverSecrets/participantKeys`), so a new account links back and a re-import refills the entry (by import ID). ### Dependency ceilings

Two dependencies are deliberately held back. **Both have their full reasoning in `pubspec.yaml` comments at the constraint itself — read those before attempting a bump.**

- **`analyzer` is capped below 9** by `custom_lint_core` (`analyzer ^8.0.0`) and `riverpod_lint` (`analyzer >=7.0.0 <9.0.0`). This holds `drift`, `drift_dev`, `build_runner`, and `sqlite3` at their current versions. `drift_dev` is a victim of the cap, not a cause. Lint coverage of the 36 hand-written providers was chosen over version currency.
- **`sqlite3_flutter_libs` is held at 0.5.x.** `0.6.0+eol` is an intentionally emptied package — upstream removed all its code because `sqlite3` 3.x bundles the native libraries. Taking it deletes the iOS/Android native SQLite build integration Drift relies on. The real migration needs `drift >= 2.32.1` → `analyzer >= 10.0.0`, so it is blocked by the ceiling above.

Riverpod codegen (`riverpod_annotation` / `riverpod_generator`) was removed as unused, not rejected on merit — every provider is a hand-written `Notifier`. Adoption is tracked separately and would be its own migration.

## Testing

- Load baselines (#88): `functions/test_acceptance/loadFixture.ts` generates the 400 and 2,000 tiers deterministically, `load.test.ts` times import, a roster page and counts and counts their reads and writes, and `docs/testing/load-baselines.md` records the results and the monthly cost estimate. `sendCategorizedPush` reads recipients 300 at a time with `getAll`; keep it batched.

- **Never call `Firebase.initializeApp()` or `FirebaseService.initialize()` from `test/` or `test_acceptance/`.** A CI grep fails the build on it. Use Riverpod overrides on the service seams instead.
- Backend tests run on the `demo-crewpoint` project, which can only reach emulators. `crewpoint-dev` holds real data, so no automated test may write to a real project.
- `test_acceptance/` holds scenario tests, whose names start with the scenario ID, and one fixture per template (`fixtures/templates.json`). When a scenario is finished, add its ID to `finished_scenarios.json` so CI protects it. `fixtures/scenarios.json` is the record of every convention scenario's status and gap (PLATFORM marks what a later stage builds); update it as work lands, then regenerate `docs/testing/CONVENTION_TEST_REPORT_v4.md` with `generate_report.py`, which refuses statuses the results contradict.
- Every callable the app names (`httpsCallable('…')` or `_call('…')`) must be exported from `functions/src/index.ts`; `functions/test/appCallables.test.ts` fails otherwise, since an unexported function is never deployed. `functions/test/roleMatrix.test.ts` checks every preset role against every restricted path, so a new path joins it.
- Unit tests use `NativeDatabase.memory()` for Drift and `fake_cloud_firestore` for Firestore. Pure utilities (`PayLinkBuilder`, `BalanceLedger`) have no Flutter/Firebase imports at all — keep them that way.
- Widget/journey tests select by stable keys named `domain.feature.action` — `Key('budget.settle.venmo')`, `Key('tasks.tile.{id}.status')`. Adding an interactive widget means adding a key.
- `test/journeys/` drives flows through `*Robot` classes (`test/robots/`) over harnesses (`test/harness/`) that seed Drift + fake Firestore and stub auth. Extend an existing robot/harness rather than pumping widgets ad hoc.
- Robots use bounded pumps instead of `pumpAndSettle` where a Drift/Firestore mirror keeps emitting — `pumpAndSettle` deadlocks there.

## Naming

Code uses only the general terms in `GLOSSARY.md`. CI fails if `family`, `meal`, `derod`, `wedding`, `cricket`, `golf` or `tee` appear as whole words in identifiers or user-facing strings in `lib/` or `functions/src/`, including `mealCount` and `meal_count`. Comments, Riverpod's `.family`, `fontFamily` and the template data are exempt. Any other exception goes in `listedExceptions` in `test_acceptance/naming_guardrail.dart`, but first move the word into a template, label or setting.

## Conventions

Conventional Commits (`feat(scope):`, `fix(scope):`, …), subject ≤ 72 chars, imperative, no trailing period. Branches `feat/` `fix/` `docs/` off `main`. PRs need at least one release-drafter label (`feature`/`fix`/`docs`/`chore`/`breaking`). Lints beyond `flutter_lints`: `always_use_package_imports` and `avoid_print` are **errors**, strict casts/inference/raw-types are on, single quotes and `prefer_final_locals` enforced.

**`pubspec.yaml` constraints carry the exact resolved version, never a rounded floor** — `google_fonts: ^8.2.1`, not `^8.0.0`. After `flutter pub get` resolves, read the real version out of `pubspec.lock` and write it back as the caret floor. Keep the caret; this is about the floor being accurate, not about pinning. A rounded floor lets a fresh resolve pick a version nobody tested, so the constraint stops describing what was actually verified. Applies to new packages and upgrades alike.
