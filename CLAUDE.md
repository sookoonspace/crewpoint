# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CrewPoint — Flutter (Dart SDK `^3.11.5`) collaborative event-management app: events with RBAC, tasks, Splitwise-style budget/settlements, real-time chat, push notifications. Backend is Firebase (Auth, Firestore, Storage, Cloud Functions v2 in TypeScript, Messaging). Three flavors map to three Firebase projects: `crewpoint-dev` / `crewpoint-stg` / `crewpoint-prod`.

## Commands

```bash
# Setup — build_runner is MANDATORY after clone/pull: *.g.dart is gitignored,
# so Drift's generated code does not exist in a fresh checkout.
flutter pub get
dart run build_runner build --delete-conflicting-outputs
cd functions && npm ci && cd ..

# Run (flavor + FLAVOR define must both be passed; .env.<flavor> supplies non-Firebase secrets)
flutter run --flavor dev -t lib/main.dart --dart-define-from-file=.env.dev --dart-define=FLAVOR=dev
flutter run -d chrome -t lib/main.dart --dart-define-from-file=.env.dev --dart-define=FLAVOR=dev  # web: no --flavor

# Test
flutter test
flutter test test/journeys/tasks_journey_test.dart          # single file
flutter test --plain-name 'substring of test name'          # single test
flutter test test/journeys/                                 # robot journey tests only
flutter test --tags screenshots --update-goldens            # regen screenshots/ (skipped by default via dart_test.yaml)
flutter test test_acceptance/                               # acceptance suite; red can be a planned gap

# Lint
flutter analyze          # must be zero issues
dart run custom_lint     # riverpod_lint checks (not covered by flutter analyze)

# Cloud Functions
cd functions && npm run build    # tsc typecheck — a required PR gate
cd functions && npm test         # jest under firebase emulators (firestore + auth)
cd functions && npm run test:acceptance   # backend acceptance suite under the emulators
firebase deploy --only functions --project crewpoint-dev

# Web
flutter build web --release --dart-define=FLAVOR=dev
```

CI (`.github/workflows/flutter.yml`) runs: build_runner → the Firebase-in-tests grep guardrail → `flutter analyze` → `flutter test`. `web-build.yml` additionally does a release web build when `lib/`, `web/`, or pubspec/firebase.json change. `functions.yml` runs `npm run build` and `npm test` on changes to `functions/**`, `firestore.rules`, `storage.rules`, `firestore.indexes.json` or `firebase.json`. `acceptance.yml` runs both acceptance suites and fails only if a scenario in `test_acceptance/finished_scenarios.json` goes red.

## Architecture

Keep the Architecture sections below, including RBAC and the Firestore data model, up to date as each Stage 1 slice lands.

### Layering

`lib/app/core/` (cross-feature) + `lib/app/features/<feature>/` where every feature is split `data/` (repositories, remote services, pure utilities) · `domain/` (models, repository interfaces) · `application/` (Riverpod notifiers/providers) · `presentation/` (screens, widgets). Features: `auth`, `budget`, `chat`, `dashboard`, `onboarding`, `participants`, `profile`, `tasks`, `dev`.

### Firestore is the source of truth; Drift is a read mirror

`EventRepository`, `TaskRepository`, `ExpenseRepository`, `ChatRepository` all follow the same shape:

- Writes go straight to Firestore (the SDK's offline queue handles reconnect).
- A per-key (`uid`, `eventId`, `eventId/taskId`) Firestore listener mirrors snapshots into Drift; the UI watches the Drift stream so cold starts render instantly. Mirrors write each snapshot in one Drift transaction: the first reconciles everything, later ones apply only `docChanges` (Req 59), so one changed document updates the screen once.
- **`kIsWeb` forks to the raw Firestore stream** — Drift on web is Wasm/in-memory, so mirroring buys nothing there. Any new mirrored stream needs the same fork.
- Mirror subscriptions are torn down through `ref.onDispose(() => repo.disposeMirror(key))` in the provider, not by the repository itself.

Drift schema is at v17 with explicit migrations in `lib/app/core/database/app_database.dart`; tables are declared inline there, DAOs in `database/daos/`. Bumping the schema means adding a migration step *and* a `test/database/migration_vN_to_vN+1_test.dart`.

### Providers

`lib/app/core/providers.dart` is the composition root — nearly every service, repository, and stream provider is declared there by hand. **Riverpod codegen is not used** despite `riverpod_generator` being in dev_dependencies: notifiers are hand-written `Notifier`/`NotifierProvider`. Follow the existing style rather than introducing `@riverpod`.

### Router

`createRouter(...)` in `lib/app/core/router/app_router.dart` is constructed **once** in `_MyAppState.initState` and driven by a `_RouterRefresh` `ChangeNotifier` passed as `refreshListenable`. Auth/onboarding changes call `refresh()` — never rebuild or recreate the router (the old pattern tore down the route stack). `onRouteChanged` defers its `currentRouteProvider` write onto a microtask because GoRouter's redirect runs during build and Riverpod 3 forbids mid-build mutation. `currentRouteProvider` exists so FCM foreground banners can suppress themselves when the user is already on the target screen.

### Test seams

Every platform call is behind an interface so tests never touch a real SDK: `IAuthService`, `IUserRepository`, `IFcmGateway`, `IChatService`, `IUrlLauncher`, `IFileExporter`, `IFilePicker`, `IImportUploader`, `IQrRenderer`, `IAppBadgePlatform`, `INotificationChannels`, `IDeviceTimezone`, `IAppInfo`, `IAppConfigSource`, `IPageReloader`, `MemberCalls` (role and member callables; `FakeMemberCalls` in `test/harness/` writes what the server would), `AppLifecycleSource`, and injected `Clock` for time-sensitive logic (e.g. the settle-confirm window). Adding a new platform dependency means adding a seam + provider, not calling the plugin from a widget.

Conditional imports handle compile-time platform splits: `database/connection/native.dart` vs `web.dart`, `services/file_export_service_native.dart` vs `_web.dart` (`if (dart.library.html)`).

### RBAC

Double-enforced through the permission catalogue (#66). The client gates UI with `event.can(uid, permission)`, `event.contributes(uid)` (adding your own expense or task, which Observer and Vendor cannot; they also read only tasks assigned to them and expenses they paid or share in, unless their role holds `tasks.manage`, `money.read` or `expenses.readAll`, so their queries filter on `assigneeId` and `involvedUids`, chosen by `taskReadScopeProvider` and `expenseReadScopeProvider`; without `chat.send` the chat entries are hidden) and `event.isOwner(uid)`. For the signed-in person these read `myPermissions` from their member document, so they update live when a role changes. `firestore.rules` checks one permission with one member-document read (reading chat needs `chat.send`), and functions use `requirePermission` in `functions/src/events/members.ts`. Check the named permission, never `creatorId`, `adminIds` or a role name. Privileged mutations are callables, not direct writes — `createEvent`, `changeEventCurrency`, `setMemberRoles`, `saveEventRole`, `deleteEventRole`, `saveCrew`, `setCrewMembers`, `deleteCrew`, `offerOwnership`, `acceptOwnership`, `cancelOwnershipOffer`, `joinEvent`, `removeEventMember`, `promoteToAdmin`, `demoteAdmin`, `deleteEvent`, `markTaskComplete`, `saveExpense`, `recordSettlement`, `disputeSettlement`, `generateInviteCode`, `deleteUserAccount`. Firestore triggers push only to people who may read the record, through `functions/src/events/access.ts`, which mirrors the rules (`onUrgentMessageCreated`, `onTaskAssigned`, `onExpenseCreated`, `onSettlementDisputed`, `onMemberJoined`, `onTaskDueScheduled`, `onDigestSummary`) drive push. `onEventStatusScheduled` moves events to `live` and `ended`. All exported from `functions/src/index.ts`; `docs/cloud-functions-guide.md` holds the authoritative Function Registry.

Firestore data model: `events/{eventId}` with `messages`, `tasks` (+ `tasks/{id}/checklist`), `taskBudgets`, `expenses`, `members`, `profiles`, `roles`, `crews`, `groups`, `participants` (+ `participants/{id}/private/details`), `linkRequests`, `participantKeys` and `ownership` (the pending offer) subcollections; `serverSecrets/{name}` (no client access); `organizers/{uid}` (a person's personal organizer, written only by the server, holding `verified`); `event_invites/{code}`; `config/app` (public read, no client write; `minVersion` and optional `storeUrls.ios` / `storeUrls.android`, set from the console); `users/{uid}` with `private`, `chatReads`, `eventMutes` subcollections, readable only by its owner.

Who reads every expense is the event's `settings.expenseAccess` (#72): `everyone` (contributors, plus Observers and Vendors only with `includeNonContributors`), `involved`, or `selected` (`roleIds` and `uids`); missing means `everyone`. Only `setExpenseAccess` changes it, logging to `settingsLog`, and `functions/src/events/expenseAccess.ts` turns it into `expenses.readAll` on member documents, so `memberDoc` and `rebuildMember` take the event's access and every caller passes `expenseAccessOf(eventData)`. Rules let anyone read expenses they paid or share in, and every expense only with `money.read` or `expenses.readAll`. `getMyBalance` gives a limited member their balance from all expenses. In the app, `event.expenseAccess` mirrors the setting (`ExpenseAccess` in `dashboard/domain/models/expense_access.dart`), `readsAllExpenses` checks only `money.read` and `expenses.readAll`, and the "Who can see expenses" screen (`settings/expenses`, `ExpenseAccessScreen`) saves through `MemberCalls.setExpenseAccess`. When someone cannot read every expense, the event budget page, its PDF export (`runExpenseExport(ledger:)`), the global Budget tab and the leave warning use `myBalanceProvider` / `myBalanceCallProvider` instead of working balances out from the expenses they see. Chat settlement notices carry an amount only when everyone who can read chat reads every expense (`chatShowsAmounts` in `access.ts`).

Money and names are kept apart from what everyone reads (#71), because rules cannot hide one field. A task's budget figure is `taskBudgets/{taskId}` (`estimate`), which needs `budget.read` to read and `budget.edit` to set or clear, and tasks never carry `budgetEstimate`. Other people's names, photos and payment handles come from `events/{eventId}/profiles/{uid}`, which only the server writes (`onMemberProfileSync`, `onUserProfileSync`): anyone in the event reads it, and someone who leaves keeps only their name there. Profiles also carry `sortName` (lower-case name) and `inEvent` (false after leaving), indexed together for the member picker (#80). `deleteUserAccount` removes every profile of the person. In the app, names load only for the people a screen shows (Req 43a): `peopleByIdProvider(PeopleKey(eventId, uids))` reads exactly those uids, one `eventProfileProvider` each (falling back to your own `users/{uid}` until the server copies it), lazy lists read each row's name in the row, and `fetchPeople` reads a few once. Pay links read handles through `IUserRepository.watchEventProfile`; never read someone else's `users/{uid}`, and never load every profile in an event. Choosing people goes through `MemberPickerSheet` (`pickOne`, `pickMany`; `IUserRepository.fetchMemberPage`, 30 a page by `sortName` prefix): the task assignee (`AssigneePicker`), who shares an expense, transfer ownership, and `ChosenPeopleList` for crews, group adults and expense access. Event tiles and counts use `event.memberCount` (the server's count, mirrored in Drift, falling back to the array). `budget/domain/models/large_event.dart` holds the 50-member line: past it a new equal split must name who shares it (with an explicit "Split with everyone"), and the budget page shows you and the 20 largest balances and transfers, reading only those names; exports read the rest when run. `taskBudgetsProvider(eventId)` streams figures straight from Firestore for `budget.read` holders and is empty for everyone else. The task screens merge it with `withBudgets`, and the Drift `tasks.budget_estimate` column stays empty. The budget field needs `budget.edit` and the "Has budget" filter `budget.read`; `updateTask(..., budgetEditedBy:)` saves a changed figure in the same batch.

Events carry `templateId`, `organizerId`, `timeZone`, `venues`, `currency`, `languages`, `status`, `modules`, `labels`, `settings`, `capacity` and `memberLimit`, and need only a title. `eventType` survives on older events as display text only. Older events lack the new fields, so reads must fall back to the same defaults as `createEvent`.

The schedule (#81) is `sessions/{sessionId}`: `title`, `startAt`, optional `endAt`, `timeTbc` (a placeholder time), `venueId` or `locationTba`, free-text `type` (suggested from types already used), `tags`, `capacity`, `eligibility` (`categoryIds` and `filterTags`, empty for everyone, one of each when both are named; `SessionEligibility.admits`) and `hidden`, a draft only `schedule.edit` reads, so anyone else lists with `hidden == false`. Clients write it directly with `schedule.edit`; rules apply the `schedule` module and the same status rules as tasks (`event.canEditSchedule`). `SessionRepository` mirrors it into the Drift `sessions` table (replacing an event's rows in one transaction, with the `kIsWeb` fork), read through `sessionListProvider(eventId)`. Venues on the event hold `address` (empty means to be announced), `mapUrl` (http or https only) and `directions`; `mapLinkFor` opens the organizer's link or a search for the address. `schedule/domain/models/schedule.dart` groups by day in the event's zone (`byDay`) and by venue (`byVenue`, every venue, then sessions without one). Screens: `schedule` (`ScheduleScreen`, by day or by venue with `VenueCard`) and `schedule/:sessionId` (`SessionScreen`: details for readers, a form for editors, `new` to add).

Attendance (#82, Req 50): the event's `settings.attendancePolicy` (`arrivalToDeparture`, `invitedOnly`, `everyone`, `bySession`; missing means everyone), a session's own `attendance` overriding it, and only exceptions stored: participants' optional `arrivalAt`/`departureAt` and session-ID lists `optOuts`, `signUps`, `invitedTo`, and groups' `invitedTo`. Only `participants.edit` changes invitations (rules); a group's linked adults set their own people's stay, opt-outs and sign-ups. `attends()` exists twice, `schedule/domain/models/attendance.dart` and `functions/src/schedule/attendance.ts`, and both run the cases in `functions/test/fixtures/attendance_cases.json`, so change them together. `setAttending` turns a switch into the smallest exception. The participant screen shows `AttendanceSection`, and `GroupSheet` sets group invitations. The `agenda` route (`AgendaScreen`, hub entry Agenda) builds the viewer's agenda with `buildAgenda` and `nowAndNext` (a session with no end lasts an hour; time from `clockProvider`/`minuteProvider`) from their own records: `MyRecordsRepository` mirrors their participant record (`uid ==`), their groups' people (`groupId in`) and groups into the Drift `my_records` table (`myRecordsProvider`). Someone with no record sees the whole schedule. Offline (Req 74): the sessions, tasks, chat and agenda mirrors record `mirror_syncs` (last server snapshot, and whether reading from cache, through `includeMetadataChanges`), and `LastUpdatedNote(mirrorKey)` shows "Offline. Last updated …" on those screens.

Counts (#83, Req 52): `functions/src/counts/stats.ts` (`computeStats`, pure) counts active people by category and by every single-choice, multi-choice and yes/no field, private ones included (totals only), and each session through the shared `attends()`; unanswered and uncategorised count under `_none`. Changes to participants, groups, sessions, fields, private answers or the policy and categories queue the event in `countsQueue/{eventId}` (`onCountsInputWritten`, `onCountsPrivateWritten`, `onCountsSettingsChanged`); `onCountsScheduled` counts each queued event once every 5 minutes into `events/{id}/stats/current` with `updatedAt`, and `recalculateCounts` (`counts.read`, `MemberCalls.recalculateCounts`) counts now. Rules let only `counts.read` read `stats`, and nobody write it or the queue. In the app, `counts` (`CountsScreen`, hub entry for `counts.read`) reads `eventStatsProvider` (gate it on `counts.read` at the caller), shows when counts were last updated and offers "Recalculate now"; the settings capacity line uses the counts total when there is one.

Export and freeze (#84, Req 53, 54), both needing `reports.export`: the counts screen exports counts as CSV in the app (`countsCsv` in `counts/domain/count_export.dart`, one row per session, private fields only when chosen), the roster through the `exportRoster` callable (private answers and birth dates only with `includePrivate` and `participants.readPrivate`), and changes since a freeze (`countChanges`, `changesCsv`). `freezeCounts` counts now and keeps the numbers in `countFreezes/{id}` (read with `counts.read`, written only by the server) with the date, who froze them and a note; the screen compares the live counts with the latest freeze or an earlier one. Every CSV cell goes through `neutraliseCsvCell` (Dart) or `toCsv` (TypeScript).

Chat paging (#85, Req 57, 58): `IChatService.latestMessages` listens to the latest `chatPageSize` (50) messages and emits `ChatChanges` from `docChanges`: upserts, deletions (`deletedFromWindow` tells a deletion from a message that only fell out of the window), and the whole window on the first snapshot and the first from the server, which clears messages deleted while away (`staleInCache`). `ChatRepository` applies each change set in one Drift transaction (`ChatMessagesDao.applyChanges`), keeps `kind` (settlement bubbles on mobile), trims the device copy to `maxCachedRows` when the mirror starts, and keeps the `kIsWeb` fork folding the same changes in memory. Older pages come from `olderMessages` / `fetchOlder` into `olderMessagesProvider` (in memory, not mirrored); `EventChatPage` shows "Show earlier messages" above the oldest message, or, offline, that earlier messages need a connection.

Chat summary (#86, Req 57a): `onChatMessageWritten` keeps `events/{id}/chatSummary/current` (`count`, `latest`, `lastUrgentAt`/`lastUrgentSenderId`; read with `chat.send`, written only by the server) and moves the sender's `users/{uid}/chatReads/{eventId}` (`lastReadAt`, `readCount`) past their own message; `migrateToMembers.ts` builds missing summaries. The app's `globalInboxProvider` reads `chatSummaryProvider` and `eventChatReadStateProvider` (`ChatReadState`, mirrored in Drift `chat_reads` with `read_count`) and works out unread counts and urgent status with `inboxUnread`, loading no messages. `EventChatPage` marks the chat read with the summary's count when opened and as messages arrive. The preview text is the message's own, so it shows an amount only when the message does.

Event dates are calendar dates: with `dateOnly: true` they are stored as midnight UTC on the chosen date, and read through `event.displayStart` and `displayEnd`, never `startDate` directly. Other times show through `event.inZone`, and a chosen day converts with `event.startOfDay`. Helpers are in `core/format/event_time.dart`.

`events/{id}/members/{uid}` holds `uid`, `roleIds`, `crewIds`, `permissions`, `participantId` and `joinedAt`, plus `groupIds` for someone linked to a group.

Participants (#75) are people attending, with or without an account, children included: `name`, `sortName` (lower-case, for paged prefix search), `groupId`, `isChild` and `status`, with `uid` (a linked account) and `externalId` (an import's ID) written only by the server. A birth date lives in `participants/{id}/private/details` as `YYYY-MM-DD`. Groups (`name`, `sortName`, `adultUids`) are written only by `saveGroup`, `setGroupAdults` and `deleteGroup`, which keep `groupIds` and `group.editOwn` on member documents in step. Rules: the roster needs `participants.read`; anyone is added or edited with `participants.edit`, or by a linked adult for their own group (`inMyGroup` reads `groupIds`); private details need `participants.readPrivate` or a linked adult of the group. A linked adult lists with `groupId in` their group IDs. Rosters are never mirrored. Custom fields (#76) are defined in `fields/{fieldId}` by `event.manage` (`type` text, number, date, singleChoice, multiChoice or yesNo; `scope` participant or group; `visibility` standard or private). Standard answers sit in `fields` on the participant or group, which a group's adults may update without the group callables; private answers sit in that record's `private/details`. The app writes `filterTags` (`fieldId=value`, standard choice and yes/no answers only) and `categoryId`, worked out from the private birth date by age rules in `settings.categories`, so the roster can filter without reading private data and reports show age bands. One composite index per combination of `groupId`, `categoryId` and `filterTags` with `sortName`. Roster import (#77): the app uploads a CSV to Storage at `events/{id}/imports/{jobId}.csv` and creates `imports/{jobId}` (`targets` maps each column, `mode` `dryRun` or `apply`, `status` `queued`); `onImportQueued` runs it with the pure `functions/src/imports/plan.ts` and writes `report` and `progress`. A client may only create a queued job, or queue a `checked` one again. Imported people carry a server-only `imported: true`, and an imported email sits in their private details. `cancelImportedGroups` confirms missing groups; `cleanupImports` removes files after 7 days. `npm test` starts the Storage emulator too. In the app, `people/import` (`ImportScreen`, before `people/:participantId` in the router) picks a file through `IFilePicker` (`file_selector`), previews and guesses the mapping with `import_mapping.dart` (matching the event's own words, so no banned word is hard-coded), uploads through `IImportUploader` and watches the job (`importJobProvider`, `recentImportsProvider`). Tests use `test/harness/fake_import.dart`, whose `FakeImportServer` answers queued jobs. Account linking (#78): `linkMyParticipants` links a signed-in person whose **verified** email (`email_verified` on the token) matches the email in a participant's private details, using the pure `functions/src/participants/linking.ts`: exactly one adult record links, never a child or a name; two or more adults, or only children, open `linkRequests/{uid}` (read with `participants.readPrivate`), which `resolveLinkRequest` settles. Linking makes someone new a Participant (an existing member keeps their roles), sets `participantId`, and adds them to the record's group (`adultUids`, `groupIds`); drafts wait for anyone not yet in the event, and ended or full events are skipped. A linked person reads their own record and its private details (`uid ==`). Deleting an account (`participants/accountData.ts`) turns linked records into unnamed entries (`name` empty, server-only `anonymised: true`, keeping age band, status, group and `filterTags`); while the event has not ended, `participantKeys/{participantId}` keeps HMAC keys of the email and import ID (secret in `serverSecrets/participantKeys`), so a new account links back and a re-import refills the entry. Children the person entered in their own group go unless another linked adult remains. Imports allow one email across a group (a family), not across groups. In the app, `accountLinkerProvider` calls `MemberCalls.linkMyParticipants` once per account per session when the signed-in user's email is verified (Google and Apple count; a password user after "I've verified", which refreshes the ID token), kept alive by `AccountLinkListener` in the signed-in shell, which shows what was linked. Organizers with `participants.edit` and `participants.readPrivate` see a count on the roster and settle requests at `people/links` (`LinkRequestsScreen`, before `people/:participantId`, through `MemberCalls.resolveLinkRequest`). `MemberModel.participantId` lets a linked person with no group see their own record on the roster and open it. Unnamed entries show as "Unnamed person". Saving private details writes back the email read with them. In the app, the pure rules are `category.dart` (`ageOn`, `categoryFor`, counted on `event.displayStart`) and `custom_field.dart` (`checkAnswer`, `filterTagsFor`). The `fields` route (`FieldsScreen`, `event.manage`) edits fields and categories; `FieldAnswerInput` renders an answer for each type. Someone who may not read private details never sees or writes them, except when adding a new person. In the app, `ParticipantRepository` reads them a page at a time (`fetchPage`, 50 per page, `startAfterDocument`), `rosterProvider(eventId)` holds the loaded pages, and `myMemberProvider(eventId)` gives your own `groupIds`. The People screens are `people` (`RosterScreen`) and `people/:participantId` (`ParticipantScreen`, `new` to add, `?group=` to start in a group); groups are picked by name search (`GroupPickerSheet`) and managed in `GroupSheet` through `MemberCalls.saveGroup`, `setGroupAdults` and `deleteGroup`. The screen reads private details only when the viewer may. Settings counts capacity from `participantCountProvider`. Only server code writes it, and `permissions` is always worked out from `roleIds` by `computePermissions` in `functions/src/events/permissions.ts`, which holds the catalogue and the twelve presets. The app reads the same presets from `functions/src/shared/role_presets.json`, generated by `npm run gen:roles`; a test fails if it falls behind. An event has exactly one Owner. Ownership moves only by an offer the new owner accepts (`offerOwnership`, `acceptOwnership`), and the old owner becomes a Co-owner; `creatorId` and `organizerId` follow it. Crews (`crews/{crewId}`, a name) are written only by the crew callables, which keep `crewIds` on member documents in step; a task's optional `crewId` must name a crew that exists. An event has one active invite, `event_invites/{code}`, carrying a `roleId` that `joinEvent` applies and an `expiresAt` the organizer sets (#79): 24 hours by default on Blank and Party, until the event starts on other templates, up to 400 days (`functions/src/events/inviteExpiry.ts`). Changing the expiry keeps the code; rotating or a new role replaces it. `previewInvite` tells someone opening `/join/:code` what they are joining and why they cannot when the event is a draft, ended or full. In the app, `AddMemberSheet` shows the link (`inviteLink`, `/join/:code` on the flavor's web host), its QR code through `qrRendererProvider` (`qr_flutter`), the code and the expiry, which the organizer changes from presets or a date (`dashboard/domain/models/invite.dart`). `/join/:code` (`JoinScreen`) is a top-level route outside the shell; the router sends signed-out or new visitors to onboarding and sign-in with `?from=` and brings them back, accepting only `/join/` paths. Web uses path URLs (`usePathUrlStrategy` in `main.dart`), and hosting already rewrites every path to `index.html`. `MemberCalls.previewInvite` and `joinEvent` back the page; tests use `FakeQrRenderer` and `FakeMemberCalls.previews`. The app loads that file into `RoleCatalogue.current` at startup, as it does label defaults, and `resolveRoles` merges it with the event's `roles` documents (`eventRolesProvider`). The Roles (`roles`), Role editor (`roles/:roleId`, `new` for a custom role) Member detail (`members/:uid`), Crews (`crews`) and Transfer ownership (`transfer`) screens live in `dashboard/presentation/roles/`; Transfer is open to the Owner, Co-owners (read-only) and the person offered, who also sees a banner on the event (`ownershipOfferProvider`); Crews needs `members.manage` or `tasks.manage` to open and `members.manage` to change. Tasks carry an optional `crewId`, and the crew picker, filter and grouping show only when the event has crews (`eventCrewsProvider`); seeing them needs `members.manage` or `roles.manage`, and changing roles needs `roles.manage`. An event's own `roles/{roleId}` documents override a preset or add a custom role. "My events" is a collection-group query on member documents (`members.uid` index), then each event document. The arrays stay until a later removal step, so every membership change still writes both, `adminIds` holds anyone with Owner, Co-owner or Admin, and the members list still reads `memberIds`. Functions fall back to the arrays for an event with no member documents. Tests: the fake Firestore sends collection-group results only once, so harnesses override `membershipsSourceProvider` with `fakeMemberships`, and rules tests get member documents from `getTestEnv`.

`modules` turns `tasks`, `budget`, `chat` and `schedule` on and off, and a module missing from the map is on. Turned-off modules keep their data. New server paths and rules for a module must check `isModuleOn`, and routes use `ModuleGuard`.

`status` is `draft`, `published`, `live`, `ended` or `archived`, and new events start as `draft`. Older events may still hold `active` until the #65 migration, which reads as `ended` past the end date, or else `published`. `firestore.rules` and `functions/src/events/eventStatus.ts` enforce what each status allows, and `EventModel` mirrors that for the UI. Plain members must never be in a draft, because list queries cannot filter them out in rules: anything that adds a plain member has to refuse drafts.

Below `config/app.minVersion`, `AppUpdateGate` in `MaterialApp.router`'s `builder` replaces the app with an upgrade screen: a store link on mobile, a reload on web. Android falls back to the Play Store page for the package, while iOS needs `storeUrls.ios`. If the document can't be read within five seconds, the app carries on.

### UI conventions

- Design tokens live in `core/constants/` (`AppColors`, `AppSpacing`, `AppRadius`, `AppTypography`, `AppSizes`, `AppIcons`, `Breakpoints`, `wcag.dart`). Screens read themed tokens from `Theme.of(context).colorScheme` — `AppColors` feeds `AppTheme.light()/dark()`; hardcoding a palette constant in a widget defeats dark mode.
- User-facing strings go through `context.strings` (`core/i18n/app_strings.dart`), shaped so an ARB-backed adapter can drop in later. Don't inline literals in UI.
- Words for general concepts (member, group, session and the rest of `GLOSSARY.md`) come from `event.words`, so organizers can rename them. Defaults live in `functions/src/shared/label_defaults.json`, which the app loads as an asset and functions import, so edit only that file. Backend text uses `resolveLabel`.
- `ResponsiveShell` switches bottom-nav → NavigationRail at 840 px; `ContentMaxWidth` + `Breakpoints.screenHorizontalPadding(context)` are the canonical page wrappers.
- Dart 3.10+ dot-shorthand enum syntax (`brightness: .light`) is used in newer code.

### Flavors and config

`AppFlavor.current` reads `--dart-define=FLAVOR=` (defaults to `dev` when absent, which is what `flutter test` gets). Firebase config is generated per flavor into `lib/firebase_options_{dev,stg,prod}.dart` by `flutterfire configure` — never hand-edit. `.env*` files are gitignored and currently only hold placeholders; `lib/app/core/env/env.dart` has the envied wiring commented out until a real non-Firebase secret exists.

### Dependency ceilings

Two dependencies are deliberately held back. **Both have their full reasoning in `pubspec.yaml` comments at the constraint itself — read those before attempting a bump.**

- **`analyzer` is capped below 9** by `custom_lint_core` (`analyzer ^8.0.0`) and `riverpod_lint` (`analyzer >=7.0.0 <9.0.0`). This holds `drift`, `drift_dev`, `build_runner`, and `sqlite3` at their current versions. `drift_dev` is a victim of the cap, not a cause. Lint coverage of the 36 hand-written providers was chosen over version currency.
- **`sqlite3_flutter_libs` is held at 0.5.x.** `0.6.0+eol` is an intentionally emptied package — upstream removed all its code because `sqlite3` 3.x bundles the native libraries. Taking it deletes the iOS/Android native SQLite build integration Drift relies on. The real migration needs `drift >= 2.32.1` → `analyzer >= 10.0.0`, so it is blocked by the ceiling above.

Riverpod codegen (`riverpod_annotation` / `riverpod_generator`) was removed as unused, not rejected on merit — every provider is a hand-written `Notifier`. Adoption is tracked separately and would be its own migration.

## Testing

- **Never call `Firebase.initializeApp()` or `FirebaseService.initialize()` from `test/` or `test_acceptance/`.** A CI grep fails the build on it. Use Riverpod overrides on the service seams instead.
- Backend tests run on the `demo-crewpoint` project, which can only reach emulators. `crewpoint-dev` holds real data, so no automated test may write to a real project.
- `test_acceptance/` holds scenario tests, whose names start with the scenario ID, and one fixture per template (`fixtures/templates.json`). When a scenario is finished, add its ID to `finished_scenarios.json` so CI protects it.
- Unit tests use `NativeDatabase.memory()` for Drift and `fake_cloud_firestore` for Firestore. Pure utilities (`PayLinkBuilder`, `BalanceLedger`) have no Flutter/Firebase imports at all — keep them that way.
- Widget/journey tests select by stable keys named `domain.feature.action` — `Key('budget.settle.venmo')`, `Key('tasks.tile.{id}.status')`. Adding an interactive widget means adding a key.
- `test/journeys/` drives flows through `*Robot` classes (`test/robots/`) over harnesses (`test/harness/`) that seed Drift + fake Firestore and stub auth. Extend an existing robot/harness rather than pumping widgets ad hoc.
- Robots use bounded pumps instead of `pumpAndSettle` where a Drift/Firestore mirror keeps emitting — `pumpAndSettle` deadlocks there.

## Naming

Code uses only the general terms in `GLOSSARY.md`. CI fails if `family`, `meal`, `derod`, `wedding`, `cricket`, `golf` or `tee` appear as whole words in identifiers or user-facing strings in `lib/` or `functions/src/`, including `mealCount` and `meal_count`. Comments, Riverpod's `.family`, `fontFamily` and the template data are exempt. Any other exception goes in `listedExceptions` in `test_acceptance/naming_guardrail.dart`, but first move the word into a template, label or setting.

## Conventions

Conventional Commits (`feat(scope):`, `fix(scope):`, …), subject ≤ 72 chars, imperative, no trailing period. Branches `feat/` `fix/` `docs/` off `main`. PRs need at least one release-drafter label (`feature`/`fix`/`docs`/`chore`/`breaking`). Lints beyond `flutter_lints`: `always_use_package_imports` and `avoid_print` are **errors**, strict casts/inference/raw-types are on, single quotes and `prefer_final_locals` enforced.

**`pubspec.yaml` constraints carry the exact resolved version, never a rounded floor** — `google_fonts: ^8.2.1`, not `^8.0.0`. After `flutter pub get` resolves, read the real version out of `pubspec.lock` and write it back as the caret floor. Keep the caret; this is about the floor being accurate, not about pinning. A rounded floor lets a fresh resolve pick a version nobody tested, so the constraint stops describing what was actually verified. Applies to new packages and upgrades alike.
